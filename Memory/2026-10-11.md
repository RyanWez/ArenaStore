## MMQR success-confirmation reliability + auto-expiry + late-SUCCESS grace

**Context:** Live sandbox testing showed a paid MMQR top-up credited the wallet
server-side (COMPLETED, ledger, balance all correct) but the customer got no
success card and the QR invoice never cleared; pressing Refresh did nothing
useful. Root cause: the success UX hung on a single fire-and-forget webhook push
(`notifyMmpayTopUpSuccess`) whose failures were swallowed, and Refresh was coded
to never re-send the card — so a dropped push had no recovery path. Separately
there was no auto-expiry (QR only flipped on Refresh) and a late SUCCESS on an
already-EXPIRED row could not credit.

**Changes:**
- `packages/db` — new column `topup_requests.mmpay_success_notified_at`
  (migration `0013_add_mmpay_success_notified`; schema `topups.ts`). One-time
  atomic claim token for the success card, decoupled from `mmpay_qr_message_id`.
  NOTE: drizzle-kit `generate` emitted a bogus full-catch-up migration (stale
  meta snapshots) — replaced the 0013 `.sql` with a minimal idempotent
  `ADD COLUMN IF NOT EXISTS`, and fixed the journal `when` for idx 13 to be
  greater than 0012 (generator used a smaller real-epoch value, which made
  `migrate` skip it). Column also applied to the live DB.
- `apps/api/src/routes/mmpay.ts` — success notify now claims
  `mmpay_success_notified_at` (guarded UPDATE), releases it on a failed Telegram
  push so Refresh can retry; added `MMPAY_LATE_SUCCESS_GRACE_MS` (30 min) grace
  for a SUCCESS on an already-EXPIRED row, and always pass `gatewayGraceExpired`
  to close the expire-during-processing race.
- `apps/api/src/services/deposit-review.service.ts` — `gatewayGraceExpired`
  param widens the reviewable/claim status set to include EXPIRED for the
  gateway webhook only.
- `apps/api/src/services/telegram-notifier.ts` — `notifyMmpayTopUpSuccess`
  returns delivered boolean.
- `apps/bot/src/services/order.service.ts` — `claim/releaseMmpaySuccessNotification`
  (flag-based).
- `apps/bot/src/bot.ts` — Refresh is now a real idempotent recovery: on
  COMPLETED it claims the flag and posts the single success card + removes the
  QR (no duplicate with the webhook).
- `apps/bot/src/services/mmpay-invoice-scheduler.ts` (new) + wired in
  `apps/bot/src/index.ts` — 60s sweep: refreshes the live countdown caption of
  active invoices and auto-expires (status→EXPIRED, delete QR, post expired
  notice) past `expiresAt`, guarded on status='PENDING' so a paying webhook
  always wins. `formatters/messages.ts` gained a countdown line +
  `formatMmpayExpiredMessage`.

## MMQR scheduler freeze + orphaned-expiry cleanup (follow-up fix)

**Symptom:** The countdown stopped mid-way (~5 min before expiry) and the QR was
never auto-expired; the bot process was alive but the sweep had stopped.

**Root cause:** the scheduler used a boolean `running` overlap guard with no
timeout on its `bot.api.*` calls. One stalled Telegram request left
`running=true` forever, so every later tick returned early — the sweep was
permanently wedged. Separately, rows flipped to EXPIRED by another path
(`/status` lazy-expiry, create-flow auto-expire) kept their QR message because
the sweep only looked at `status='PENDING'`.

**Fix (`apps/bot/src/services/mmpay-invoice-scheduler.ts` rewrite):**
- Every `bot.api` call is wrapped in `withTimeout` (10s); the overlap guard is
  now an age check (`MAX_TICK_MS` 2 min) instead of a boolean, so a stalled call
  can never freeze the sweep.
- The sweep is now a janitor over every row with `mmpay_qr_message_id IS NOT
  NULL` regardless of status: PENDING→countdown/expire, already-EXPIRED→delete
  QR + expired notice, CANCELLED/FAILED/COMPLETED→delete stale QR. Each terminal
  path CAS-nulls the QR id so webhook/Refresh/sweep act exactly once.
- `order.service.claimMmpayInvoiceCleanup(reference)` + Refresh EXPIRED branch
  now claims before replying, so Refresh and the sweep never double-post an
  expired notice.

**Verified:** tsc clean (api/bot); unit 269/269, integration 58/58. The live
stuck invoice (MMQR-MV40ZJAG207A8EBD) was auto-cleaned by the rebuilt sweep on
reload (qr id nulled, QR removed, expired notice sent).
