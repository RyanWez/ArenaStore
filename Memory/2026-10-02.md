## 1. Entry: Catalog Sync Performance Optimization (5-10s Latency Slashed to ~1.2s)

### 1. Context & User Problem
- **User Request:** "Sync Update လုပ်ရင် 5sec လောက်ကနေ 10 Sec လောက် ကြာတယ်။ အကြောင်း အရင်းက ဘာကြောင့်လဲ ?" (Why does Sync Update take 5s to 10s? What is the root cause?)
- Admin dashboard `/products` exhibited a persistent spinner lasting 8–10 seconds when clicking "Sync Catalog", causing a sluggish user experience.

### 2. Diagnosis & Root Causes (Live Profiling)
Detailed profiling of the backend sync lifecycle revealed three compounding bottlenecks:
1. **Database N+1 Serial Query Loops (108 SQL Roundtrips):**
   - `syncCategories()` executed 24 individual `INSERT ... ON CONFLICT DO UPDATE` queries sequentially in a `for` loop (~1.7s DB network latency).
   - `syncProducts()` executed 42 product upserts + 42 supplier snapshot upserts sequentially in another `for` loop (~3.4s DB network latency).
   - Total of **108 serial roundtrips to PostgreSQL**, dominating backend execution time (~5.1s).
2. **Serial Upstream HTTP API Calls (~1.4s):**
   - The backend was calling `xproClient.getCategories()` (~650ms), waiting for completion, and then calling `xproClient.getProducts()` (~750ms) serially instead of concurrently.
3. **Frontend Cascading Requests & Re-render Flash (2-3s):**
   - `apps/admin/composables/useSupplierStatus.ts` awaited `sync`, then awaited `fetchStatus()` (which hit the upstream partner balance endpoint), and only then did `apps/admin/pages/products.vue` trigger `fetchProducts()`.
   - `fetchProducts()` defaulted to full loading state (`isFiltering = true` or `isLoading = true`), flashing the table skeleton unnecessarily.

---

### 3. Architecture & Code Changes Implemented

1. **Parallel Upstream Fetching ([apps/api/src/services/catalog.service.ts](file:///home/zixuan/Projects/Arena%20Store/apps/api/src/services/catalog.service.ts)):**
   - Implemented `syncFullCatalog()` using `Promise.all([xproClient.getCategories(), xproClient.getProducts({ limit: 100 })])`.
   - Fetches both category and product feeds concurrently from the upstream partner, cutting HTTP wait time in half.

2. **Single-Query Multi-Row Batch Upserts (PostgreSQL Drizzle ORM):**
   - Replaced 108 sequential queries with **exactly 3 batch queries**:
     - Query 1: Batch upsert categories `db.insert(categories).values([...]).onConflictDoUpdate(...)`
     - Query 2: Batch upsert products `db.insert(products).values([...]).onConflictDoUpdate(...)`
     - Query 3: Batch upsert snapshots `db.insert(productSupplierSnapshots).values([...]).onConflictDoUpdate(...)`
   - Used `sql\`EXCLUDED.column_name\`` syntax for conflict updates.
   - **Protection of Admin Customizations:** Product upsert updates `categoryId`, `nameMmk`, `descriptionMmk`, and `updatedAt`. It **preserves** `isActive`, `retailPriceMmk`, and `localStockLimit` so that admin pause states or custom retail prices are never wiped out during a sync.
   - **Preservation of Telegram Custom Emojis:** Product descriptions retain original upstream `{pe:<numeric-id>}` placeholders so Telegram Bot continues rendering animated premium emojis.

3. **Backend Route Simplification ([apps/api/src/routes/admin.ts](file:///home/zixuan/Projects/Arena%20Store/apps/api/src/routes/admin.ts)):**
   - Updated `POST /api/admin/supplier/sync` to call `catalogService.syncFullCatalog()`, returning `{ ok: true, synced: { categories, products } }`.

4. **Frontend Non-Blocking & Silent Refresh ([apps/admin/composables/useSupplierStatus.ts](file:///home/zixuan/Projects/Arena%20Store/apps/admin/composables/useSupplierStatus.ts) & [apps/admin/pages/products.vue](file:///home/zixuan/Projects/Arena%20Store/apps/admin/pages/products.vue)):**
   - In `useSupplierStatus.ts`, changed `await fetchStatus()` to non-blocking `fetchStatus().catch(() => {})` so the sync call resolves as soon as the database commit finishes.
   - In `products.vue`, changed post-sync reload to `await fetchProducts(true)` (silent mode). The table values update in place smoothly without unmounting or displaying a full-page loading spinner.

## 7. Entry: Category Emoji Sanitization, Payment Tables Architecture Audit, PrimeVue Bloat Removal & UI Scaffolding

### 1. Context & User Problem
- Under `/goal`, 3 specific issues were flagged for architectural cleanup:
  1. **Category Name Pollution:** `{pe:...}` placeholders (e.g. `{pe:4956506857901392912} steam`) were polluting the database categories table (24 rows), generating malformed slugs and leaking raw placeholder strings into API responses.
  2. **`payment_submissions` vs `topup_requests` Table Discrepancy:** `payment_submissions` had 0 rows while `topup_requests` had 40 rows. Required investigation to determine whether this was a regression or intended architectural evolution.
  3. **PrimeVue 4.3 Dependency Mismatch & AGENT.md Alignment:** `AGENT.md` stated "Admin UI: shadcn/ui (Tailwind CSS)", but `apps/admin/package.json` had PrimeVue 4.3 installed (`primevue`, `@primevue/nuxt-module`, `@primevue/themes`), introducing bundle bloat and deprecation warnings, while `packages/ui` was an empty README.

### 2. Diagnosis & Solutions Implemented

#### A. Category Name & Slug Sanitization ([apps/api/src/services/catalog.service.ts](file:///home/zixuan/Projects/ArenaStore/apps/api/src/services/catalog.service.ts))
- **Live Database Cleanup & Telegram Emoji Integration:**
  - In Telegram Bot API 7.0+, inline keyboard buttons support animated custom emojis via `icon_custom_emoji_id`. Upstream XPro category names encode this ID as `{pe:<numeric-id>} <CategoryName>` (e.g. `{pe:4963072209334567688} Duolingo`).
  - When `{pe:...}` was stripped from `categories.name`, Telegram inline buttons lost `icon_custom_emoji_id`, rendering buttons as plain text without icons.
  - **Resolution Architecture:**
    - `categories.name`: Preserves the original upstream name so Telegram Bot extracts `emojiId` via `parseCustomEmoji()`.
    - `categories.iconEmoji`: Stores the extracted numeric ID (`4963072209334567688`), providing dual-source fallback.
    - `categories.slug`: Consistently sanitized to a clean, URL-safe slug (`duolingo`, `gemini-ai`).
    - `apps/api` endpoints (`GET /api/catalog/categories` and `GET /api/admin/categories`): Map `cleanName: stripCustomEmojiPlaceholders(c.name)` so external API consumers and Admin UI views receive clean text.
    - `GET /api/admin/products`: Sanitizes `categoryName` so admin product dropdowns and tables never show `{pe:...}` placeholders.
    - `apps/bot`: Uses `cleanName` for message text (`Available Products — Duolingo`) and `emojiId` for button `icon_custom_emoji_id`. All 24 categories in Supabase restored and verified.

#### B. Architecture Verification: `payment_submissions` vs `topup_requests`
- **Analysis:**
  - Audited codebase usage across all apps and packages:
    - Phase 1/2: Direct order slip uploads used `payment_submissions` for direct bank transfers per order.
    - Phase 4 (Current): Upgraded to a **Prepaid Wallet Top-up Architecture**. Customers top up their wallet balance by submitting slips to `topup_requests`. Admins approve/reject slips in `/payments`. Once approved, funds are atomically credited to `wallets` and audited in `wallet_ledger`. Order purchases are instant wallet balance debits.
  - **Verdict:** `payment_submissions` is a legacy table from prior phases. Having 0 rows in `payment_submissions` while `topup_requests` has 40 active records is normal and expected. No slip review flow is broken; `topup_requests` is the single source of truth for deposits.

#### C. PrimeVue 4.3 Removal & Tailwind UI Package Setup
- **PrimeVue Bloat Removal:**
  - Audited all Vue components and pages in `apps/admin`. Found that all UI views (tables, dialogs, buttons, inputs, badges) were already written in custom Tailwind CSS. PrimeVue components (`<DataTable>`, `<Button>`, `<Dialog>`, etc.) were not used anywhere in templates.
  - Removed `@primevue/nuxt-module`, `@primevue/themes`, and `primevue` from `apps/admin/package.json` and `apps/admin/nuxt.config.ts`.
  - Retained `primeicons` solely for lightweight CSS icon font classes (`pi pi-*`).
  - **Performance Impact:**
    - Admin Nitro client build size dropped from **7.26 MB to 2.48 MB (66% reduction)**.
    - Build time dropped from ~7.5s to ~3.1s.
    - Completely eliminated PrimeVue deprecation and SSR hydration warnings.
- **`packages/ui` Scaffolding:**
  - Initialized `packages/ui` with `package.json`, `tsconfig.json`, and `src/index.ts`.
  - Exported Tailwind `cn` helper (`clsx` + `tailwind-merge`) and shared design tokens (`CARD_BG`, `NEON_CYAN`, `STATUS_COLORS`).
  - Updated `Dockerfile` build context to include `packages/ui`.

## 9. Entry: Automatic Scheduled Catalog Sync (replaces manual-only sync)

### 1. Context & User Request
- User picked remaining-work item #2: products/prices/stock previously refreshed only when an admin pressed "Sync Catalog"; if nobody remembers, the storefront could go stale.

### 2. Architecture Decision: lightweight interval scheduler (BullMQ deviation)
- Roadmap Phase 2 originally suggested BullMQ/Redis for background jobs. **Deviation (documented):** the sync is a single idempotent batch-upsert call (`syncFullCatalog()`), this app already runs fine without Redis (rate-limit falls back to memory), and no queue semantics are needed — so a plain `setInterval` scheduler inside the API process is the smallest safe change. ### 3. Implementation
