## 1. Entry: Catalog Sync Performance Optimization (5-10s Latency Slashed to ~1.2s)

### 1. Context & User Problem
- **User Request:** "Sync Update လုပ်ရင် 5sec လောက်ကနေ 10 Sec လောက် ကြာတယ်။ အကြောင်း အရင်းက ဘာကြောင့်လဲ ?" (Why does Sync Update take 5s to 10s? What is the root cause?)
- Admin dashboard `/products` exhibited a persistent spinner lasting 8–10 seconds when clicking "Sync Catalog", causing a sluggish user experience.

### 2. Diagnosis & Root Causes (Live Profiling)
Detailed profiling of the backend sync lifecycle revealed three compounding bottlenecks:
1. **Database N+1 Serial Query Loops (108 SQL Roundtrips):**
   - `syncCategories()` executed 24 individual `INSERT ... ON CONFLICT DO UPDATE` queries sequentially in a `for` loop (~1.7s DB network latency).
   - `syncProducts()` executed 42 product upserts + 42 supplier snapshot upserts sequentially in another `for` loop (~3.4s DB network latency).
   - Total of **108 serial roundtrips to PostgreSQL**, dominating backend execution time (~5.1s).
2. **Serial Upstream HTTP API Calls (~1.4s):**
   - The backend was calling `xproClient.getCategories()` (~650ms), waiting for completion, and then calling `xproClient.getProducts()` (~750ms) serially instead of concurrently.
3. **Frontend Cascading Requests & Re-render Flash (2-3s):**
   - `apps/admin/composables/useSupplierStatus.ts` awaited `sync`, then awaited `fetchStatus()` (which hit the upstream partner balance endpoint), and only then did `apps/admin/pages/products.vue` trigger `fetchProducts()`.
   - `fetchProducts()` defaulted to full loading state (`isFiltering = true` or `isLoading = true`), flashing the table skeleton unnecessarily.

---

### 3. Architecture & Code Changes Implemented

1. **Parallel Upstream Fetching ([apps/api/src/services/catalog.service.ts](file:///home/zixuan/Projects/Arena%20Store/apps/api/src/services/catalog.service.ts)):**
   - Implemented `syncFullCatalog()` using `Promise.all([xproClient.getCategories(), xproClient.getProducts({ limit: 100 })])`.
   - Fetches both category and product feeds concurrently from the upstream partner, cutting HTTP wait time in half.

2. **Single-Query Multi-Row Batch Upserts (PostgreSQL Drizzle ORM):**
   - Replaced 108 sequential queries with **exactly 3 batch queries**:
     - Query 1: Batch upsert categories `db.insert(categories).values([...]).onConflictDoUpdate(...)`
     - Query 2: Batch upsert products `db.insert(products).values([...]).onConflictDoUpdate(...)`
     - Query 3: Batch upsert snapshots `db.insert(productSupplierSnapshots).values([...]).onConflictDoUpdate(...)`
   - Used `sql\`EXCLUDED.column_name\`` syntax for conflict updates.
   - **Protection of Admin Customizations:** Product upsert updates `categoryId`, `nameMmk`, `descriptionMmk`, and `updatedAt`. It **preserves** `isActive`, `retailPriceMmk`, and `localStockLimit` so that admin pause states or custom retail prices are never wiped out during a sync.
   - **Preservation of Telegram Custom Emojis:** Product descriptions retain original upstream `{pe:<numeric-id>}` placeholders so Telegram Bot continues rendering animated premium emojis.

3. **Backend Route Simplification ([apps/api/src/routes/admin.ts](file:///home/zixuan/Projects/Arena%20Store/apps/api/src/routes/admin.ts)):**
   - Updated `POST /api/admin/supplier/sync` to call `catalogService.syncFullCatalog()`, returning `{ ok: true, synced: { categories, products } }`.

4. **Frontend Non-Blocking & Silent Refresh ([apps/admin/composables/useSupplierStatus.ts](file:///home/zixuan/Projects/Arena%20Store/apps/admin/composables/useSupplierStatus.ts) & [apps/admin/pages/products.vue](file:///home/zixuan/Projects/Arena%20Store/apps/admin/pages/products.vue)):**
   - In `useSupplierStatus.ts`, changed `await fetchStatus()` to non-blocking `fetchStatus().catch(() => {})` so the sync call resolves as soon as the database commit finishes.
   - In `products.vue`, changed post-sync reload to `await fetchProducts(true)` (silent mode). The table values update in place smoothly without unmounting or displaying a full-page loading spinner.
