# 2026-10-12 — Daily Log

## MMQR reconciliation sweep — webhook-lost recovery (production blocker #1)

**Context:** The MMQR feature confirmed payments through the gateway webhook
only. A dropped / blocked / late webhook (quick-tunnel hostname change, Render
cold-start timeout, signature mismatch) left a paid customer uncredited until
the order expired, and the bot's "Refresh" only re-read the local DB, so it
could not recover a lost webhook. The webhook was a single point of failure.

**Fix — add an active reconciliation path so we no longer depend solely on the
webhook. The gateway stays the fast path; polling is the safety net; crediting
is idempotent so the two can race and still credit once.**

- `apps/api/src/services/mmpay.service.ts` — new `getPaymentStatus(orderId)`:
  token handshake + `POST /xpayments/{env}-payment-show` (returns status +
  amount + currency). New `ready` getter exposes whether creds are configured.
  Endpoint/shape sourced from the live `/xpayments/*` API + the official browser
  SDK (the docs site's `/payments/*` paths are stale). **Needs one sandbox
  validation with real keys** (nonce/Btoken pairing on repeat polls).
- `apps/api/src/services/mmpay-settlement.service.ts` (NEW) — `settleMmpaySuccess()`:
  the single SUCCESS-credit path now shared by the webhook, the sweep and the
  on-demand Refresh, so status vocabulary can't drift between them again (the
  old root cause). Encapsulates the already-credited guard, late-expired grace,
  amount/currency validation, `reviewDeposit` atomic claim, the one-time success
  card, and a one-time admin "manual reconcile" alert. Returns a discriminated
  code the caller maps to its transport. `MMPAY_LATE_SUCCESS_GRACE_MS` moved here.
- `apps/api/src/routes/mmpay.ts` — webhook SUCCESS block refactored to call
  `settleMmpaySuccess` and map the code → HTTP (200/409/400/500 unchanged). The
  status route (bot "Refresh") now pulls the gateway status when the row is
  still PENDING and settles on SUCCESS → instant self-recovery. Create route
  reads `config.PUBLIC_API_URL` (now in the zod schema) instead of raw env.
- `apps/api/src/services/mmpay-reconcile-scheduler.ts` (NEW) — periodic sweep:
  selects still-live MMQR orders (PENDING + in-grace EXPIRED, bounded by age),
  pulls each from the gateway, settles any SUCCESS. Overlap guard + per-call 10s
  timeout + rate-limit delay. `reconcilePendingMmpay()` takes an injectable
  `getStatus` for tests. Wired into `server.ts` (guarded on NODE_ENV!=test,
  interval>0, and `mmpayService.ready`).
- `apps/api/src/services/telegram-notifier.ts` — `notifyMmpayReconcileAlert()`
  posts to the admin "Bot Alert" topic when a gateway-paid order can't be
  auto-credited (amount/currency mismatch, or SUCCESS beyond grace). Best-effort.
- `packages/db` — migration `0014_add_mmpay_reconcile_alerted.sql` + schema:
  `topup_requests.mmpay_reconcile_alerted_at` (one-time alert claim, same
  pattern as `mmpay_success_notified_at`). Journal idx 14, `when` 1792100000000.
- `apps/api/src/config.ts` — new `MMPAY_RECONCILE_INTERVAL_SECONDS` (default 45,
  0 disables) + `PUBLIC_API_URL` added to the schema. Documented in `.env.example`.

**Tests:** new `tests/integration/mmpay-reconcile.integration.test.ts` (5):
lost-webhook credit, idempotent vs webhook (no double-credit), gateway-PENDING
no-op, amount-mismatch no-credit + one-time alert claim, and the on-demand
Refresh-route credit (spies `mmpayService.ready`/`getPaymentStatus`). Webhook
refactor keeps all existing mmpay-webhook assertions. **Full suite 332/332

## Deploy-config hardening (#2) + status-guarded cancel/expire (#3)

**#2 — MMPay fail-closed boot guard (Render env is the deploy target).**
`apps/api/src/config.ts` now rejects a HALF-configured gateway in any non
dev/test environment: if exactly one of `MMPAY_PUBLISHABLE_KEY` /
`MMPAY_SECRET_KEY` is set it throws at boot (a missing secret would silently
skip webhook signature verification → a forged SUCCESS could credit a wallet).
Both-empty still cleanly disables MMPay. If both keys are set but
`PUBLIC_API_URL` is empty it logs a loud warning (webhook callback URL can't be
built; falls back to the portal URL). No docker-compose wiring — owner deploys
via Render env only.

**#3 — cancel/expire can no longer overwrite a credited row (TOCTOU).**
`apps/api/src/routes/mmpay.ts`: the customer-cancel UPDATE and the status-route
lazy-expiry UPDATE are now status-guarded (`WHERE id AND status='PENDING'` with
`returning`). A SUCCESS webhook that credits the order in the window between the
route's SELECT and its UPDATE no longer gets clobbered to CANCELLED/EXPIRED — the
wallet credit and the row status can never disagree. On a lost race the cancel
route returns the real settled status + `cancelled:false` (+ `amountMmk`).
The bot (`order.service.cancelMmpayTopUp` now returns `{ok,cancelled,status,
amountMmk}`; `bot.ts` cancel handler) honors it: if the order was actually paid
it shows the "already paid" success card (claimed once) instead of telling the
customer it was cancelled.

**Tests:** +2 cancel-guard integration cases (cancel a PENDING order; a cancel
after a webhook credit does NOT revert the credit). **Full suite 334/334 green;
api+bot tsc clean; `pnpm -r build` exit 0.**

## MMQR UX edge-cases (#4)

**Orphaned invoice when the QR message id was lost.** The invoice sweep only
touched rows with `mmpay_qr_message_id IS NOT NULL`, so a PENDING row whose id
was never stored (photo sent but the follow-up attach write failed / the bot
crashed between) was never auto-expired and held the single-active lock until
the customer acted. `apps/bot/src/services/mmpay-invoice-scheduler.ts` now has a
second pass each tick that flips such orphaned PENDING MMPay rows (null id, past
`expiresAt`) to EXPIRED (no Telegram message to delete), freeing the lock.

**Orphaned old QR photos on re-issue / re-show.** `attachMmpayQrMessage`
overwrote the stored message id, so repeat `mmpay_show` / `mmpay_pay` left the
previous QR cards untracked and never cleaned. It now returns the PREVIOUS id;
the `mmpay_pay` and `mmpay_show` handlers (`apps/bot/src/bot.ts`) delete that old
photo after sending the new one, so only one live QR card remains.

(The single-instance assumptions — in-memory `activeTopUpLocks`, per-process
sweep guard — are fine on the single Render backend service and were left as-is.)

**Tests:** +1 integration case (`attachMmpayQrMessage` returns the previous
message id / null correctly). **Full suite 335/335 green; api+bot tsc clean;
`pnpm -r build` exit 0.**
