## Database Migration: Neon Serverless to Aiven Managed PostgreSQL & Connection Pool Tuning

### 1. Incident Background (Neon Serverless Outage)
- **Root Cause**: Neon Free Tier allocates 100 Compute Unit Hours (CU-hrs) per month. On 2026-10-21, production Neon compute reached 110.68 CU-hrs and was automatically suspended, throwing HTTP 500 across all bot interactions (`endpoint has exceeded its compute hour quota`).
- **Why it depleted**: Serverless databases sleep after 5 minutes of inactivity to conserve CU-hrs. However, Arena Store runs active background schedulers:
  1. MMQR Invoice Countdown Janitor (`TICK_MS = 30s` in `apps/bot/src/services/mmpay-invoice-scheduler.ts`)
  2. MMPay Deposit Reconciler (`POLL_INTERVAL_MS = 45s` in `apps/bot/src/services/mmpay-reconciler.ts`)
  3. UptimeRobot Keep-Alive (`/health` ping every 10m)
- These timers kept the database awake 24 hours a day, 7 days a week, consuming ~720 compute hours/month (exceeding Neon's 100 CU-hr ceiling).

---

### 2. Migration Destination: Aiven Free Tier PostgreSQL
- **Plan**: Aiven Free Tier on DigitalOcean Bangalore (`blr` region, low latency to Myanmar/Singapore).
- **Specifications**: 1 vCPU, 1 GB RAM, 5 GB NVMe Storage, Maximum 20 Connections.
- **Key Advantage**: Always-on (never sleeps, no compute unit caps), perfect for scheduled cron jobs, background workers, and Telegram bots.

### 3. Migration Procedure & Technical Pitfalls Solved

#### Phase A: Schema Migration
- Ran all 16 existing Drizzle migrations (`packages/db/migrations`) against the fresh Aiven database.
- Generated all 19 relational tables, indexes, constraints, and audit triggers.

#### Phase B: Full Topological Data Transfer (`scratch/migrate-data.ts`)
- Extracted and transferred data table-by-table following foreign-key dependency order:
  1. `app_settings`
  2. `users`
  3. `roles` & `role_permissions`
  4. `wallets` & `wallet_ledger`
  5. `categories` & `products` & `product_supplier_snapshots`
  6. `topup_requests`
  7. `orders`, `order_items`, `order_deliveries`
  8. `broadcasts`, `audit_logs`, `referrals`
- **Pitfall 1 — JSONB Array Serialization with `node-postgres`**:
  - In `pg`, raw JavaScript arrays passed to parameterized SQL queries default to Postgres arrays (e.g. `{"item1", "item2"}`) rather than JSON arrays (`["item1", "item2"]`), causing Postgres error `malformed array literal`.
  - *Fix*: Explicitly applied `JSON.stringify(val)` to JSON/JSONB fields (like `role_permissions.actions` and metadata objects) before executing `INSERT`.
- **Pitfall 2 — Primary Key Sequences Out of Sync**:
  - Inserting historical data with explicit `id` values does not advance Postgres `SERIAL` / `IDENTITY` sequences automatically. Subsequent `INSERT` calls would fail with `duplicate key value violates unique constraint`.
  - *Fix*: Executed dynamic sequence resynchronization across all tables:
    ```sql
    SELECT setval(pg_get_serial_sequence('<table>', 'id'), COALESCE(MAX(id), 1), true) FROM <table>;
    ```

#### Phase D: Aiven Custom CA SSL Handshake (`SELF_SIGNED_CERT_IN_CHAIN`)
- **Problem**: When connecting Node.js (`pg` pool) to Aiven using `sslmode=require`, Node.js rejects Aiven's self-signed CA certificate chain with `Error: self-signed certificate in certificate chain`.
- **Solution in [`packages/db/src/client.ts`](file:///home/zixuan/Projects/ArenaStore/packages/db/src/client.ts) and [`packages/db/src/migrate.ts`](file:///home/zixuan/Projects/ArenaStore/packages/db/src/migrate.ts)**:
  - Automatically detect Aiven hosts (`*.aivencloud.com`) or `DB_SSL_REJECT_UNAUTHORIZED=false`.
  - Strip `?sslmode=require` from `connectionString` so the driver does not override the custom SSL options.
  - Provide `{ ssl: { rejectUnauthorized: false } }` to the `pg.Pool` configuration.

### 4. Connection Pool Architecture & Capacity Analysis

#### Pool Settings
- `DB_POOL_MAX` environment variable configured with default value of `6` (configurable up to `10`).
- Aiven Hard Limit: **20 connections**.

#### Why a Pool of 6 to 10 is More than Enough for Thousands of Users
1. **Stateless Connection Borrowing (Multiplexing)**:
   - Web browsers and Telegram bots DO NOT maintain persistent database connections.
   - When a user interacts with the Bot or opens the Web UI, Node.js backend borrows a connection from the pool, executes the query (taking ~2ms to 10ms), and **immediately releases it back to the pool**.
   - A single connection handling 5ms queries can execute **200 queries per second (QPS)**.
   - A pool of 6 connections can comfortably process **600 to 1,200 QPS**, easily serving thousands of active concurrent store shoppers without queueing.

#### Why the Remaining Connections (~10-14) are NOT Wasted
1. **Developer & Admin Operations (No Lockouts)**:
   - When developers run migrations (`pnpm db:migrate`), backup scripts, or connect via GUI tools (DBeaver, pgAdmin, TablePlus), these tools consume separate connections. Having a buffer prevents `FATAL: sorry, too many clients already`.
2. **Zero-Downtime Deployments (Container Overlap)**:
   - During deployments on Render, a new container spins up and establishes its DB pool before the old container shuts down. The buffer ensures both containers can coexist during rollout without exceeding 20 connections.
3. **Multi-Service Architecture Ready (Web Storefront + Bot)**:
   - When the upcoming Web Storefront is launched alongside the Bot/API, both separate processes can allocate 5–6 connections each without colliding or exhausting Aiven's 20-connection ceiling.
